# Impeccable Style Skill

## Use this skill when

- The task already has a primary visual owner such as `frontend-ui-ux`, and the work clearly needs a higher-finish polish pass.
- The user wants premium presentation quality, refined composition, stronger visual taste, or a memorable finishing layer.
- The task involves real visual output such as components, templates, page sections, styles, or interaction details.

## Primary owner job

- Act as an optional polish modifier for UI work that is already in the correct visual lane.
- Raise the finish quality of layout, typography, composition, and interaction details.
- Improve visual taste without competing with `frontend-ui-ux` for first-pass ownership.

## What this skill does

- Refines an already-visual task with better composition, stronger hierarchy, cleaner rhythm, and more deliberate presentation.
- Helps push beyond generic safe styling when the task calls for a polished result.
- Works best after the main visual direction is already clear.
- Keeps the scope focused on quality of finish, not on changing the task domain.

## What this skill does not do

- It does not replace `frontend-ui-ux` as the default visual entry point.
- It does not own routine frontend tasks where standard visual discipline is enough.
- It does not justify rewriting non-visual logic.
- It does not apply to backend, docs, CLI, infra, or data-only work.

## When to combine with another skill

- Combine with `frontend-ui-ux` when the task is visual and needs both a primary design direction and a finishing pass.
- Do not load this skill by itself for normal UI work unless the task is explicitly about polish or refinement.

## Pass criteria

- The skill is clearly positioned as optional polish, not as a default router.
- The triggering reason for using `impeccable-style` is concrete and visual.
- The output improves finish quality in a way a reviewer can describe, such as stronger hierarchy, cleaner rhythm, or better presentation balance.
- The scope stays visual and does not drift into unrelated logic changes.

## Anti-patterns

- Loading `impeccable-style` as a default for every frontend task.
- Treating it as a peer router to `frontend-ui-ux`.
- Using polish language to justify a redesign that the user did not request.
- Triggering it for backend, docs, CLI, or non-visual work.
- Rewriting logic-heavy code under the excuse of visual refinement.
